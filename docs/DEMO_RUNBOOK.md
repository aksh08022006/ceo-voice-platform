# Demo recording runbook

This is a repeatable 3–5 minute recording plan. It deliberately labels the local provider and named
profiles as synthetic showcase fixtures.

## Before recording

1. Run `make api` and `make frontend-dev` in separate terminals.
2. Open `http://127.0.0.1:3000` in a clean browser window.
3. Confirm `http://127.0.0.1:8000/api/v1/health` returns `status: ok`.
4. Use a 1440×900 viewport, 100% zoom, and light mode.

## 3–5 minute sequence

| Time | Screen | Narration objective |
|---:|---|---|
| 0:00–0:25 | Landing | State the problem: evidence-backed, explainable, governed executive communication. |
| 0:25–0:50 | Architecture | Follow the single ingestion-to-evaluation SVG; emphasize prompt-last generation. |
| 0:50–1:15 | Profiles | Open one showcase profile and state the synthetic-data/governance boundary. |
| 1:15–2:10 | Generate | Load the Ali walkthrough, generate, and expand evidence plus the execution timeline. |
| 2:10–2:50 | Re-Voice | Show the preloaded human edit, run Re-Voice, and inspect protected decisions. |
| 2:50–3:30 | Evaluation | Read the overall disposition, one dimension, and the evidence trace. |
| 3:30–4:05 | Benchmarks | Show the three backend-served cases and explain why no score appears before execution. |
| 4:05–4:30 | Conclusion | Return to the architecture and summarize traceability from corpus to report. |

## Recording checklist

- Keep the synthetic showcase disclaimer visible when discussing named profiles.
- Do not describe deterministic local output as a real-person fidelity result.
- Avoid terminal footage except for the two server startup lines.
- Record one uninterrupted workflow so the same session ID governs every report.
- Export at 1080p, 30 fps, with captions if narration is included.
